# 档案核心识别：下一阶段方案

这是上一轮的设计提案。其主要流程现已开发为v5.3，最新行为与边界以 [开发说明](ARCHIVE_V5_GUIDE.md) 和 [本轮测试报告](ARCHIVE_V5_EVALUATION.md) 为准。本轮授权更新为最多200次API请求、350万token，已完成并停止自动付费测试。下方保留设计推导与原计划，不能把旧阶段预算当作当前授权。

## 1. 核心收敛到一个结果

多上传几段聊天后，用户能更准确地回答：“我对这个人有哪些有依据的了解，下次和TA相处时有什么值得留意？”

产品只围绕三个能力：形成有范围的认识；随新聊天修正；沟通时用上相关认识。现有五种使用场景是测试材料和功能价值的方向，不成为五个入口。暧昧了解优先，但不会给所有人物显示恋爱判断。

我们可争取的优势是：用户不用反复整理材料，认识有原文、条件和变化过程，错误能修正，后续建议能受最新认识约束。大模型本身也能做长期记忆；这些能力要靠实测证明更省事、更少误解，不能仅凭一张档案页面宣称独有或有效。

## 2. 先判断值不值得记

候选信息至少符合一项：

- 会改变下次怎么回应：如对方这次只想倾诉；公开场合不希望被起哄。
- 会帮助理解这个人：如偏爱的具体玩法、喜欢作品的理由、主动表达的个人看法。
- 会改变已经形成的认识：如“并不是不爱聊，只是不熟的人太多时不知道怎么插话”。
- 有后续需要衔接的事情：如已谈到的面试、比赛、共同约定及变更。

“喜欢星露谷”可以保存，但首页优先呈现“喜欢慢慢种田，因为觉得放松；不喜欢被催进度”这种更有沟通价值的内容。普通问候、无关重复、泛泛夸赞不必每次变成档案条目。模型必须允许输出零条；也不能靠全部拒绝来制造高准确率。

## 3. 已确认：允许有限推断

保存时区分原文事实与可能理解，界面不增加一套填写流程：

| 层次 | 示例 | 约束 |
|---|---|---|
| 可观察的依据 | 两次私聊主动分享游戏；一段群聊回复较少 | 标清谁、哪段聊天、何时、在什么情境；记录只覆盖上传内容 |
| 有限推断 | 私聊熟悉的话题时，TA可能更愿意展开表达 | 附支持依据、反例或未能排除的解释；不写成固定人格 |
| 可用建议 | 下次可从TA主动分享过的话题接着聊，给对方选择回应方式的空间 | 绑定依据；只能建议尝试，不承诺效果、不推算好感 |

另一种解释可能是当时忙碌、群里话题不熟或上传片段不完整。若无材料支持某个替代解释，只说“尚不能排除”，不能把它作为新事实保存。多次上传同一段不增加支持强度；多段相似行为也不等于心理测量。

有限推断不能绕过明确边界。例如对方明确说只想做朋友，不能用“经常主动分享”推翻它。这里记录的是表达过的态度和观察到的行为，不声称读出隐藏感情。

## 4. 借鉴研究后，如何改识别流程

### A. 给模型较窄的任务，保住上下文

第一步只找值得记录的具体表达或互动，不同时要求它写人格报告、判断关系、合并全部历史和产出建议。每条返回发言者、原文位置、主张、时间、适用条件，区分本人表达、转述、台词、假设和用户自己的补充。

短聊天完整提供。长聊天按话题和相邻发言分组，保留必要的问答、否定、代词指向以及重叠范围；不能只把孤立关键词交给模型。分段摘要仅是导航，不能替代原话成为证据。先用长度不同的样本测是否真的需要分段，不直接引入向量数据库。

[Lost in the Middle](https://arxiv.org/abs/2307.03172)发现其测试模型的长上下文表现受到信息位置影响；这提示我们验证长聊天效果，而非断言所有新模型都存在同样程度的问题。[Anthropic Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval)说明孤立切片会丢失对象与时间背景；这里借鉴保留上下文的原则，不照搬其文档检索收益。

### B. 核查的是“这句话能否支持认识”

程序核查：引用存在、发言者正确、编号和日期有效、未重复、未覆盖受保护的用户修正。

语义核查：把涉及关系态度、性格推断、前后反转的候选送入独立核查步骤。核查者看原话和必要上下文，不接收首轮的说服性分析；回答“支持、只支持更窄表述、相反、信息不足”，必须给出对应原文。多条合并核查，避免每个字段一次请求。

例：“小说台词是‘我想和你在一起’”中的引用是真的，但主张“对方想和我在一起”不成立。不能只用关键词黑名单：真实表白也可能同时谈到电影或小说。规则负责确定性约束，语义判断回到具体上下文。

[Chain-of-Verification](https://arxiv.org/abs/2309.11495)通过独立回答核查问题降低其事实任务中的幻觉；可借鉴核查不受草稿影响的设计，但不能推导出聊天识别同样有效。[自我纠错研究](https://arxiv.org/abs/2310.01798)在推理任务中发现没有外部反馈的自检可能失败甚至变差。因此相同模型多问一遍不是独立真值，多模型投票也不是保证。我们的依据仍是原始对话与人工标注样本。

### C. 核查后再与旧档案比较

只把相关旧认识及其依据带入比较，避免模型被整份旧画像带偏。对于候选，选择新增、补充依据、细化条件、状态改变或暂待确认。时间顺序由真实聊天时间决定；用户未给日期时不拿上传时间冒充。不能为了主题相同就合并不同对象、不同约定。

模型提出更新建议，程序负责版本、去重、时间保护和用户修正保护。模型不能直接删除历史或自行把矛盾改成已经确定。

用户已确认：核查通过的明确事实和有限推断自动保存，只有新旧矛盾或明显改变核心认识时才简短询问。待确认的冲突不影响其他正常内容入库；有争议的认识暂不支撑建议，也不能继续用旧说法当作确定答案。人工修正继续受保护。首批将用“关系态度反转、边界反转、有限推断被澄清”几个案例校准询问频率，避免每次细化都弹窗。

[LongMemEval](https://arxiv.org/abs/2410.10813)将信息提取、跨会话推理、时间推理、知识更新和不知道时不回答分别评估。我们据此将“提取对了”和“后来的更新对了”分开验收。

### D. 只从通过核查的内容生成少量方法

明确表达可直接支撑对应建议；有限推断必须保留“可能”和适用范围；待确认项不支撑确定性建议。每条方法关联依据编号，依据变更后方法失效或重建。优先用少量具体方法，避免生成一整套泛化的情商话术。

流程是逻辑分层，不要求四次付费调用：首轮先试“提取一次 + 核查、对照更新和方法一次”的两次调用。先让核查结论成为门槛，拒绝项不能出现在方法中。若合并任务导致核查流于形式，再单独试验证步骤；不预设调用越多越好。

## 5. 兼容不同模型的做法

- 统一小型数据结构和短提示，给少量正反例：真实表白/引用表白、明确边界/玩笑、变化/不同情境。不要要求模型输出长篇思维过程。
- 服务商支持结构化输出时使用；不支持时解析JSON并在程序里验证。格式正确与内容正确分别记录。DeepSeek的[官方JSON模式说明](https://api-docs.deepseek.com/guides/json_mode/)主要约束输出格式，不能替代原文核查。
- 不依赖模型自报“95%置信度”。用证据类型、上下文是否完整、有无反例和核查结果决定展示方式。
- 模型能力较弱时，先限制到明确表达和具体互动；能否开放有限推断由同一组验收样本决定，不靠型号名称猜测。降级要向用户说明，不能悄悄让弱模型输出同样肯定的画像。
- 只测试本地实际配置且在授权范围内的服务；一个服务的结果不能宣称所有模型适用。不擅自把聊天发给其他提供商。
- 长期保存证据若不足以核查旧认识，应标记依据不足。核查用必要上下文；不能为了开发方便，悄悄从“保存少量脱敏依据”改为永久保留全部聊天。

## 6. 连续案例：如何形成、再收窄认识

1. 第一次，TA说“群里你们聊得太快，我插不上话”。保存这次参与困难与情境。不能写成“内向、不合群”。
2. 第二次和第三次，TA在私聊里主动讲游戏剧情和自己的看法。可形成“私聊熟悉话题时可能更愿意展开”的有限推断；保留忙碌程度、话题熟悉度等尚未排除因素，不推断喜欢用户。
3. 后来TA说“其实熟人群我也很能聊，那天群里都是不认识的人”。旧认识收窄为“熟悉程度可能更重要”，旧版留档，不把每次新行为都变成一个互相冲突的人格标签。
4. 后续提问“怎么跟TA接着聊”：取出共同话题、对方观点和熟悉程度的限制；建议从其分享过的内容接续。不得回到“TA是内向型，要主动带动”这种未经支持的固定判断。

这组是新流程的验收目标，不是当前系统已经能稳定做到的演示承诺。

## 7. 分步开发与停止点

| 步骤 | 做什么 | 何时停下来对齐 |
|---|---|---|
| 已完成 | 一个统一档案页，去掉场景入口，重点方法前置、辅助内容折叠 | 用户检查页面；已确认允许有限推断及正常内容自动保存 |
| 下一步 | 完成证据、有限推断、核查结果的数据契约和10组人工可核查虚构样本 | 先给用户看真实候选结果的格式与错误分类，不扩大功能 |
| 小样本对照 | 10组样本各跑原流程一次、新两阶段流程一次，预计30次请求；拟设阶段token上限15万，仍受总上限约200次/200万约束 | 对比误记、漏记、过度推断、错误更新和成本后汇报；没有改善就定位问题，不扩量 |
| 后续才扩测 | 改动确有收益后，用预先冻结的未参与调参案例做评估；含多次上传和日期倒序 | 再确认表现与取舍，然后集成正式预览 |

初步样本分布可用5组暧昧、2组日常、1组兴趣、1组跨年龄、1组事项。这是开发覆盖安排，不是大学生使用比例。每组同时标注“应该提取”和“不能推断”，评价漏记，避免全部留空看似安全却无用。错误逐条复核；模型自评分不能充当唯一裁判。真实用户沟通效果另需后续验证。

统计每次请求、服务商返回token、失败和重试，禁用隐藏自动重试；调用前按输入与最大输出保守预留，usage缺失时不当零消耗。到阶段上限或同类错误反复发生即停下报告。新增授权是可用上限，不是需要花完的目标。

本轮不修改单次分析指标与队友算法，不增加新的场景页面、人格测试、练习、提醒或长报告按钮。
